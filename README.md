# Kitchen Rush

A dependency-free, real-time kitchen co-op prototype for up to four chefs, with optional bots and three guided solo demo rounds.

Run `python server.py`, then open http://localhost:8000. With Docker, build using `docker build -t kitchen-rush .` and run `docker run --rm -p 8000:8000 kitchen-rush`.

## Deploy online

The frontend can run as a Vercel static site while the authoritative multiplayer server runs as a Render Docker web service. The included `render.yaml` defines the backend and health check. Create the Render Blueprint from the repository, then create a Vercel project from the same repository with its root directory set to `public`. Set the Vercel project environment variable `BACKEND_URL` to the backend's HTTPS origin (for example, `https://your-service.onrender.com`, without a trailing slash); `public/vercel.json` routes `/api/*` through Vercel to that origin.

The included Render Blueprint uses the free plan. Free web services spin down after 15 minutes without inbound traffic and take about a minute to start again. A restart clears active rooms because room state is held in server memory. Choose a paid Render plan to avoid idle spin-down for an always-available game server. Keep the backend at one instance: rooms are not shared across processes.

The footer includes the Kitchen Rush copyright notice and links to the public source repository at https://github.com/austinhttps/kitchen-rush. The homepage has three entry flows: **Play demo** needs no name and enters as Chef Trainee; **Join a room** needs only a nickname and room code; **Create a room** asks for a nickname, difficulty, and bot count. The server exposes separate `/api/demo`, `/api/join`, and `/api/create` endpoints; an empty join code cannot accidentally create a room. Setups validate before room state is stored.

Room codes are generated automatically with six mixed uppercase letters/numbers, displayed as `XXX-XXX`, for example `A7K-2QM`. The separator is additional to the six code characters. Codes always contain both a letter and a digit, avoid ambiguous generated characters, and are checked against existing rooms. Joining accepts raw/formatted and lowercase/uppercase codes. Share the invite or code, then join from another browser/device. On your local network, devices must use your computer's LAN IP with port 8000, not localhost.

Real players enter a nickname; `Chef` is added automatically without duplicating an existing prefix. Use WASD/arrows to move, E to interact/pick up, F to throw, X to discard, and P/Escape to open the menu. A detailed eighteen-section handbook sits below the homepage entry buttons and is also available through Help. The in-window game frame contains the crew, recipes, ticket strip, toolbar, actions, and touch controls in windowed and fullscreen play.

Creating, joining, and rejoining update the URL to `/?room=XXX-XXX`. Session credentials are stored in both per-tab session storage and `localStorage` under `kitchen-rejoin`. Refreshing/reopening offers **Rejoin game**, **Not now**, and **Forget this kitchen**. Two consecutive state-fetch failures or the browser offline event show the same prompt and suspend local input/polling until the player decides. `/api/rejoin` authenticates the saved token and reuses the existing chef/inventory/position without allocating a slot. Not now preserves the record and slot; explicit Leave releases the slot and clears that session's saved record. A missing/expired room gives an explicit error and a Forget path. Room state is still in memory: rejoining survives connectivity loss or refresh while the server/room exists, not a server restart.

Only room codes appear in the address. State snapshots expose public chef IDs rather than authentication tokens; a player never receives another chef's private session token. The private token stays in that player's browser storage and authenticated requests. Per-tab records take precedence over the last local-storage record so refreshing one chef tab does not silently switch to another tab's chef.

Hosts can select **0–3 bot teammates** when creating a room or change the count between rounds. Bots and humans share the four-chef cap and difficulty target; reduce bots to free slots for friends. You can play alone with bots or invite human teammates into the remaining slots. Only humans can host; leaving the last human removes the room even if bots remain. Guided demos remain solo. Bots reserve separate tickets/counters/stoves, navigate the same station collisions, and use normal ingredient, chopping, cooking, plating, serving, washing, and fire-extinguishing interactions. They observe task/cooking timers, one-item inventory, and projectile stuns. The crew sidebar shows their current work. They replan routes after a station shuffle, and briefly wait while stations move. Human interference can make them replan; expired jobs are cleaned up or redirected to another ticket for the same recipe.

Choose **Play demo** for an isolated solo tutorial without entering a name: salad preparation, burger cooking, then fish-and-rice service with dishwashing. Each lesson has a fixed recipe, illustrated kitchen, five instructions, and a 2-minute-30-second limit. A correct service ends the lesson immediately. Retry or proceed after success or timeout. The final lesson starts with dirty plates and no clean ones; wash to continue. Finish or exit the demo to return home before creating/joining a real kitchen. Demo rooms reject additional players, have no surprise events, and never change real-room scores.

During real play, **Fullscreen** uses the browser Fullscreen API on the actual playfield, for both real kitchens and demos; **Shift+F** toggles it from the keyboard. A single console-style HUD shows the room code, **The Little Bistro**, timer, score/target, combo, difficulty, bot count, and circular active-chef portraits. Order alerts stack at the left of the playfield, while other alerts use separate lanes. Demo lesson instructions also float over the playfield. At 30 seconds the clock blinks red; at 10 seconds **LAST CALL** appears at center through the final second. It clears at results/restart/leave and hides during shared pause. Pause freezes the blinking; reduced-motion settings keep warnings static red. The small bottom-left context popup hides when there is no relevant station/item. The in-game Menu opens compact crew, recipe/drink, score, ticket, seating, and shutdown-rule cards alongside controls, host actions, sound, fullscreen, results, and Leave kitchen. Active stove shutdown warnings show a compact fire icon and countdown. Results use compact score, statistic, outcome, and chef-delivery cards. The windowed game keeps the site header/footer outside the game frame; fullscreen expands the playfield instead of stacking the page chrome around a smaller canvas.

The serving station is now a **wall-mounted window at (13, 4)**, aligned with the customer order/pickup counter on the kitchen’s right boundary. Chefs approach from inside the kitchen (for example, 12,4); it stays fixed through every moving-station event.

The canvas contains original bistro artwork: a striped awning, tiled kitchen, perimeter work surfaces, stoves with cooking progress/steam, a dining room with tables and plants, and a customer queue tied to actual order tickets and patience. Added side counters are usable stations, not just decoration. The scene redraws at animation-frame cadence while authoritative room state arrives separately.

The HUD occupies a single flexible navbar above the canvas, including fullscreen and narrow screens; the bottom key tips bar is hidden because controls live in the pause menu. Cooking, chopping, washing, and stun states show compact on-scene countdowns. A start-of-service popup keeps the host in the game frame until they call the crew to the pass. Order tickets and notifications occupy opposite sides of the playfield to avoid overlap. The map name **THE LITTLE BISTRO** remains in the HUD. A ResizeObserver positions tickets and alerts below the rendered map header, accounting for wrapped HUD controls and canvas letterboxing. Local static/API responses use `Cache-Control: no-store` so changed assets and server state stay in sync during development.

**Host controls** appear only to the host inside the game frame and within the menu. The host can remove another human or bot with the bright X on that chef’s crew card; confirmation appears before removal, and the server checks host permission, updates the bot count, and invalidates a removed human’s saved room token. Crew cards remain stable between roster changes, so live state polling does not interrupt the X click. Removed humans are returned to the homepage with an explanation and can join again with a new invite. The server separately checks permission for start/rematch, pause/resume, restart, end round, and between-round settings. Real starts/restarts/rematches have a synchronized four-second **Aprons on → 3 → 2 → 1 → GO!** overlay. Movement, bots, tickets and gameplay wait until launch; the full round and ticket patience start afterward. Demo lessons enter immediately. Restart and End round require confirmation. **Restart round** opens next-shift setup: choose difficulty and keep/uncheck each human or bot. The host stays checked and cannot remove themselves. The server validates the entire selection before changing anything, then applies removals and difficulty together, recalculates target/bot count, rebuilds the layout/menu, resets progress, and starts a fresh countdown. Restart setup is available after a shutdown too. End round shows the crew’s results immediately. A removed human’s old rejoin credential no longer works. A new join is still possible if the host invites them again. Removal credentials are never exposed in public snapshots.

Opening the host's menu during live service pauses the entire kitchen. Opening a guest's menu blocks only that guest's input unless the host has already paused. A shared pause freezes round time, orders, cooking/burning, tasks, bots, throws, stuns, station motion, and surprise scheduling. The server shifts deadlines on resume. Audio is muted while paused. Repeated explicit pause/resume requests are idempotent. Guests wait for the host but can leave with confirmation. If the host leaves, another human inherits host and can resume. The menu stays available after results are dismissed and can reopen results. It also lists the crew and roles/delivery counts, available recipes and drink preparation, current difficulty/score/target/ticket count, occupied seats, and shutdown rules. Pausing freezes sustained-fire deadlines and seated-customer dining time too.

**Kitchen surprises** give a three-second warning and scale with difficulty and round progress:

| Level | First warning | Nominal repeat delay after an event | Duration | Possible surprises |
| --- | ---: | ---: | ---: | --- |
| Easy | 45s | 55s | 4s | Receipt confetti, counter shuffle |
| Medium | 28s | 40s | 5s | Ingredient-crate shuffle, counter shuffle, steam |
| Hard | 24s | 33s | 5s | Stove shuffle, ingredients, counters, steam |
| Expert | 20s | 27s | 6s | Prep shuffle, stoves, ingredients, steam |
| Chef | 17s | 22s | 6s | Steam/stoves/ingredients rush, station carousel, prep, steam |
| Chef de Cuisine | 14s | 18s | 7s | Station carousel, rush, prep, steam |

Repeat delays shorten by up to 35% over the round, with a twelve-second minimum. The first surprise uses the first listed type; subsequent ones are random. Intensity increases with difficulty and elapsed time. Selected stations are highlighted during the warning, then cycle through each other's existing positions over 1.4 seconds. Ingredient shuffles move all six dispensers; prep swaps pick two chopping boards/plate/sink/extinguisher stations; rushes cycle stoves and ingredient dispensers together; carousel moves every station except Serve. The serving counter stays at its original customer-facing position in every movement event, including the carousel. Their contents, timers, and identity/reservations stay attached; no new blocked floor tile is created, and chefs are not displaced. Interacting with moving stations is rejected until they settle. Bot routes are invalidated after motion. Reduced-motion users see simpler visual distractions and station position changes without the glide. Visual effects are clipped to the kitchen and cannot intercept buttons or cover critical DOM HUD/alerts. Demos are undisturbed. Rematches restore the original station layout and reset event scheduling. Whole-floor rotation is not implemented; carousel cycles the stations while the walkable floor remains fixed.

**Throwing** creates a visible server-simulated projectile travelling up to five tiles. Moving sets facing; clicking/tapping aims, and moving again clears aim. Ingredients can be thrown; plates, extinguishers, and drink cups cannot. An empty-handed human or bot catches a hit into its inventory without a stun or duplicate floor item. A carrying chef is stunned for 1.25 seconds and the ingredient falls to the floor. Bots safely deposit caught food on an empty counter before resuming their recipe. A projectile crossing the middle of an empty counter/stove is caught during flight. The catch zone is the central 0.4-by-0.4 tile square; near misses do not snap onto the station, and occupied/moving stations do not catch. Chopped meat/fish or raw rice starts the normal seven-second cook when caught by an empty stove. Other food rests there with no cook timer and can be retrieved. Uncaught food lands on the floor and can be picked up with E. There is a 200-item floor/projectile cap; excess throws are rejected. Floor/projectile state clears on rematch.

The handbook has a separate close-button header and scrolling content, so Close remains clickable while reading long instructions. Native dialog dismissal also supports Escape. Room-code/connection errors appear next to the lobby entry buttons.

**Back to homepage**, the header logo, and results-to-home actions show a **Leave this kitchen?** confirmation. Keep cooking or Escape cancels without changing the session; Leave game releases the player slot. Tab close, reload, or navigation registers a browser-native `beforeunload` warning while joined. Browsers control whether that warning is shown, require prior interaction, and supply its text; embedded browsers may suppress it. A webpage cannot guarantee interception of the desktop application's own exit.

When a round concludes, every player receives an automatic results dialog with the final team score, target, cooperative winner/outcome, orders completed, incorrect dishes, expired orders, burned food, best multiplier actually used, drinks served, the exact shutdown reason when applicable, and individual delivery counts for the chefs present at the finish. A winning crew shares the victory; there is no individual winner on a loss. Results are frozen by the server at the round boundary. The host’s **Rematch setup** reviews difficulty and crew before resetting the same room for everyone; guest buttons are disabled until they become host. **Review kitchen** dismisses the popup, and **View results** reopens it without repeated automatic popups. Demo results instead offer retry, next lesson, or finish. Dialogs clear movement input and block game shortcuts while open; the shared timer continues.

Chop meat/fish/vegetables, cook meat/fish/rice, put a plate on a counter, add the recipe ingredients, retrieve the plate, and serve. Wash dirty plates. Chopping and washing take three seconds. Cooking takes seven seconds; food burns after a shorter post-cooking window: 15/10/8/6/5/4 seconds from Easy through Chef de Cuisine (previously 25/15/12/10/8/6). Hold an extinguisher and interact with the affected stove to clear it.

Rounds last 2 minutes 30 seconds. Correct orders earn 100 times the current multiplier plus up to 30 speed points. Oldest-first service increases the multiplier up to four. Incorrect orders cost 50; expired orders cost 25. The host chooses difficulty when creating a kitchen and can change it between rounds. Guests share the host's setting; standalone changes during service are rejected by the server; the confirmed restart setup can apply a new difficulty for the next shift.

**Immediate round losses** apply to real kitchens. Reaching **−200 points or lower** ends service immediately and clamps the final score at −200, even if a large guest penalty crosses the floor. Any individual stove left on fire for **20 continuous seconds** also ends the round, even when the score exceeds the target. Fire starts after the post-cooking burn window; a prominent shutdown clock appears with additional warnings at 10 and 5 seconds remaining. Extinguish the stove to clear its deadline; other burning stoves keep their own deadlines. Shared pause preserves remaining time. All clients receive the same frozen results/reason, and further gameplay stops. Guided demos keep forgiving practice rules without these shutdowns. `outcomes.py` owns finalization and safety checks.

**Drinks on Medium and above:** those layouts add a **Drinks** station and **Lemonade** tickets (including possible VIP/critic drink requests). With empty hands, interact there to hold a cup and mix for three seconds. Carry the finished lemonade directly to the wall window; no plate or assembly is needed. Cups do not consume the clean/dirty plate supply and cannot be thrown. Ordinary scoring/combo/tip/expiry rules still apply. Easy and all demo lessons exclude drinks. Bots can mix and serve them using the same actions. Difficulty changes rebuild the station list and recipe eligibility on the next round.

**Dining seats:** successfully served customers can occupy the four chairs around the two dining tables for 12 seconds. Meal/drink and VIP/critic identity follow the served ticket; the server assigns unique seats and all clients share occupancy. When all chairs are occupied, additional served customers take their orders away. Seating does not award extra points or delay the existing immediate dirty-plate return. Pause freezes dining time; restart clears seats. `dining.py` owns occupancy and `public/dining-art.js` renders the diners.

**VIP guests and food critics** now have real orders and scoring, replacing the old cosmetic critic interruption. Gold VIP and purple Critic tickets show explicit bonus/failure amounts, with crowns/monocles on their matching dining-room customers. A correctly served special order earns the ordinary score plus its bonus. The oldest matching recipe receives the plate; clear earlier duplicate recipes before reaching that guest. A wrong plate offered while a special guest is the front ticket removes that guest and costs its listed penalty instead of the normal 50. Expiry or remaining unserved at the buzzer costs that same penalty once. Final guest penalties apply before the win calculation, including host End round. Results record special guests served/missed.

The opening third ticket is a VIP. Remaining visits alternate Critic/VIP at intervals of `240 / (visits + 1)` seconds after the preceding visit. Later arrivals wait for a free slot; the active-customer cap counts both waiting ticket holders and seated diners, rising from 3 on Easy to 8 on Chef de Cuisine. A full customer cap can defer a VIP visit beyond the round. Critics have 15% less patience. Special-visit deadlines shift with shared pauses. Demos have no special guests. After the first new ticket, subsequent arrival intervals subtract the player count from the base (minimum five seconds). Demo mode uses Easy cooking tolerance with 180-second tickets and one fixed order. Its goal is one correctly served dish, even if earlier mistakes reduced the practice score.

State is synchronized by HTTP every 100 ms; a server simulation thread updates at 20 Hz independently of browser polling while unpaused and after launch. Bot decisions are paced separately. Room state disappears when the process restarts. Explicit Leave releases a slot; rooms without humans are removed. Closing/disconnecting without leaving reserves the slot for rejoin. Moving platforms, conveyors, dash, automatic cleanup, and public hosting remain future work. The user's future WASD car/roads/huts world-and-level map is recorded in [ROADMAP.md](ROADMAP.md) and is intentionally deferred.
